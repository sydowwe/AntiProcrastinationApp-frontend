# R8 · Keyboard, screen readers, and narrow screens

- **Scope:** all six views and most components under `src/_common/modules/reminders/`
- **Backend:** —
- **Model / effort:** **Opus 5**, high
- **Depends on:** R5 (rewrites the same files), R2 and R7 (both change the template branches this touches)
- **Unblocks:** nothing

```
An accessibility and responsive pass over the reminders module. Nothing here is a crash — it is the
difference between a module a keyboard or screen-reader user can operate and one they cannot.

--- Submodule note, read this first ---

These files live in src/_common, the vue_framework git submodule. CLAUDE.md says never to write to it;
this task is the approved exception. Edit them in place; do not fork into src/ and do not add a
migration-revision.md entry. Leave the work in the submodule's working tree and say so at the end. Commit
and bump the pointer only if asked. ESLint and Prettier IGNORE src/_common — match the surrounding style
by hand (tabs, single quotes, no semicolons, camelCase props in templates, PascalCase component tags).

Before changing any Vuetify component's props, verify the exact API with the `vuetify` MCP — several
components here (VIconBtn, VChip, VAlert, VDataTable slots) are used in ways that assume props exist.

--- The confirmed problems ---

**1. Icon-only buttons announce nothing.**

Every row action in this module is a VIconBtn carrying a `:title` and no accessible name:

    MyRemindersView.vue:104-125       snooze + dismiss
    ReminderUpcomingView.vue:157-166  view history
    ReminderDefinitionsView.vue:100-109 show
    ReminderActionButtons.vue:14-25, 39-50, 65-76  pause / resume / cancel, when iconOnly

`title` produces a tooltip on hover and is inconsistently announced; it is not a substitute for an
accessible name, and on a touch device it is nothing at all. Each needs a real label. Note these buttons
also render `<VIcon size="15" />` as a child with no icon name (the icon comes from the parent's `icon`
prop) — check with the vuetify MCP whether that empty child is doing anything at all, and if it is not,
say so rather than propagating it into new markup.

**2. The action columns have no header text.** BasicTable is passed `:hasEdit="false"
:hasDelete="false" :hasCreate="false"` in all five views, so the actions header renders empty
(BasicTable.vue:18-45) while the column still holds two or three interactive controls. A screen reader
user tabbing into that column gets no context for what the buttons act on — which row, which reminder.
Row-scoped labels ("Pause reminder {kind}") solve this better than a column header does; prefer that.

**3. `+N` recipient overflow is mouse-only.** RecipientChips.vue:21-28 hides the remaining ids behind a
VChip whose only affordance is `:title="allIdsLabel"`. Keyboard and screen-reader users cannot reach the
hidden ids at all. Either make the full list reachable (expandable, or a focusable tooltip) or render it
in a way that does not depend on hover.

**4. Status is conveyed by colour plus an icon that is also decorative.** ReminderStatusChip and
DispatchOutcomeChip both map a value to an icon and a colour, and the text label is present — that part
is fine. Check that the icons are not announced redundantly ("circle check Sent") and that the
colour-only distinctions elsewhere are not load-bearing: OverviewFailureList.vue:52-56 renders the failure
detail in `text-error` with no other marker, and DispatchOutcomeChip uses `textMuted` for Skipped, which
should be checked for contrast against the surface in both themes.

**5. Nothing announces that the table updated.** Filter, sort and page changes swap the rows silently.
A polite live region reporting the result count after a load would fix this for all five views at once —
if you build one, build it once and use it five times, and put it in modules/reminders/component/ rather
than in _common/component/ (a framework-wide announcer is a bigger decision than this prompt).

**6. Narrow screens.** These are dense admin tables and will never be great on a phone, but check and fix
what is cheap:
   - The header rows (`d-flex align-center justify-space-between mb-4 flex-wrap ga-3`) already wrap.
     Verify they actually do at 375px rather than overflowing.
   - ReminderOverviewView's three headline cards use inline `style="min-width: 200px; flex-basis: 200px"`
     (lines 43-86) and OverviewGroupCard uses `style="min-width: 280px; flex-basis: 45%"` (line 3-5).
     Confirm these collapse to one column rather than causing horizontal page scroll.
   - ReminderDefinitionDetailView's `.reminder-info-grid` is `repeat(auto-fit, minmax(220px, 1fr))` — that
     is already responsive; leave it.
   - The payload `<pre>` (`.payload-block`, line 354-364) has `overflow-x: auto` and `white-space:
     pre-wrap` — verify a long single-token payload does not scroll the page body horizontally.
   The rule: wide content scrolls inside its own container, the page body never scrolls horizontally.

**7. Focus after a dialog closes.** SnoozeDialog and the dismiss MyDialog both unmount via `v-if` /
`v-model` while the row that opened them may have just been removed from the table by `dropActiveRow()`
(MyRemindersView.vue:254-257). Focus is then lost to the document body. Check what MyDialog already does
about focus return — read _common/component/dialog/MyDialog.vue before writing anything, this may already
be handled — and only fix it here if it is not.

--- How to work ---

Fix in the order listed; 1 and 2 are most of the value. Prefer Vuetify props over hand-written ARIA
wherever a prop exists — verify with the vuetify MCP rather than guessing. Do not add `role`/`aria-*`
attributes to a Vuetify component that already manages them; doubling them up is its own bug.

All new user-facing strings go in _locales/{reminders,remindersDashboard}.sk.ts in Slovak, matching the
surrounding tone. The module is Slovak-only by design — do not create an .en.ts. Labels that interpolate a
count need the plural forms described in R3; read src/i18n.ts:9 first if you write one.

--- Out of scope ---

- Rewriting BasicTable or DataTable in _common/component/dataTable/. If the right fix genuinely lives
  there, say so in your final message and do the module-local fix — a framework table rewrite is not this
  prompt.
- Colour palette changes. `textMuted`, `error`, `success`, `warning` are theme names the whole framework
  uses; if one fails contrast, report it, do not redefine it.
- A full WCAG audit or an automated-tooling setup.

--- Verification ---

npm run type-check — baseline 72 errors, all app-side in src/core; any src/_common error is yours.
npm run lint stays at 0.

Then, by hand, on /pripomienky/moje and /pripomienky/register:
  - Tab through an entire table row without a mouse. Every control is reachable, has a visible focus ring,
    and activates with Enter and Space.
  - With the browser's accessibility inspector (or VoiceOver/NVDA if available), read each row-action
    button's computed accessible name. It should say what it does AND to which reminder.
  - Open the snooze dialog by keyboard, complete it by keyboard, and confirm focus lands somewhere sane
    after it closes.
  - At 375px width: no horizontal scroll on the page body on any of the six routes; the overview's cards
    stack.
  - Toggle the app's dark theme and re-check the chips and the failure list for legibility.

List in your final message what you fixed, what you found and deliberately left, and anything that needs
a framework-level change.
```
