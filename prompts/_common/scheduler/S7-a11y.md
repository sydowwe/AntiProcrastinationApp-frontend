```
The scheduler module at src/_common/modules/scheduler/ is an admin console that assumes a mouse, a
wide screen and colour vision. Fix that. It is framework code, so whatever you establish here is the
pattern other modules will copy.

SUBMODULE RULES — read before editing:
src/_common is the vue_framework repo mounted as a git submodule, and CLAUDE.md says never to write
to it. This task is an explicit, user-approved exception: the scheduler module lives there and
nowhere else. So:
  - Edit the files in src/_common in this working tree. Do NOT fork a file into src/, and do NOT add
    a migration-revision.md entry.
  - Leave the work in the submodule's working tree and say so in your final message; the parent repo
    will show a dirty submodule pointer. Commit inside the submodule only if the user asks.
  - ESLint and Prettier ignore src/_common, so `npm run lint` will not check your work. Match the
    surrounding style by hand: tabs, single quotes, no semicolons, tab-indented <script setup>.
  - `npm run type-check` DOES cover src/_common. Baseline is 72 errors, all app-side in src/core;
    _common is clean. Any new error under src/_common is a regression you introduced.

WORK THROUGH THESE. Confirm each against the live page — several are judgement calls that depend on
what Vuetify already does for you, and guessing produces aria soup that makes things worse.

1. FOCUS VISIBILITY ON CUSTOM INTERACTIVE ELEMENTS.
   AttentionJobList.vue:83-92 styles `.attention-row:hover` and nothing else. Those rows are
   RouterLinks — fully keyboard-reachable, and a keyboard user tabbing the health dashboard gets no
   indication of where they are. Add a visible :focus-visible treatment at least as strong as the
   hover one. Check every other custom-styled link in the module for the same omission — the
   RouterLinks in SchedulerJobsView.vue:63-68, JobRunHistory.vue:79-84 and
   SchedulerRunDetailView.vue:52-57, :144-150 all carry `text-decoration-none`, which removes the
   underline that would otherwise be the affordance.
   Do not disable or replace Vuetify's own focus rings on VBtn / VIconBtn / VListItem; only add where
   there is nothing.

2. ICON-ONLY BUTTONS AND THEIR NAMES.
   The module uses a `<VIconBtn icon="eye" :title="…"><VIcon size="15" /></VIconBtn>` pattern in
   three places (SchedulerJobsView.vue:133-142, JobRunHistory.vue:112-131, and the icon-only branch
   of JobActionButtons.vue:15-27, :40-51, :65-76). Two things to check on the live page, not in your
   head:
     - Does each button end up with an accessible name? `title` usually provides one as a fallback,
       but confirm with the browser's accessibility inspector rather than assuming, and add
       aria-label where it does not.
     - The nested `<VIcon size="15" />` with no icon prop, inside a VIconBtn that already has
       `icon="eye"`, is odd — work out what it actually renders and whether it emits an empty
       element into the accessibility tree. Fix it if it does; leave it if it is load-bearing for
       sizing, but say which in your report.
   The row-action buttons in both grids are ALSO ambiguous by name alone: every row has an identical
   "Show" and "Replay". A screen-reader user tabbing the table hears "Show, Show, Show". Give them
   names that identify the row — the job key or the run's start time is already in the row data.

3. STATUS CONVEYED BY COLOUR.
   The three chips (JobStatusChip, RunOutcomeChip, TriggerSourceChip) pair an icon with translated
   text, so they are mostly fine — verify rather than assume. The real colour-only cases:
     - AttentionJobList.vue:24 and :59 apply `text-${color}` to the count and the detail line, where
       colour is the ONLY thing distinguishing a failure from a warning.
     - SchedulerNeedsAttentionView.vue:61, :75, :89 render the three status counts in
       success/warning/muted, distinguished from each other by colour and icon but labelled by a
       caption that does not repeat the severity.
   Make sure severity survives greyscale. The labels are already there in most cases; where they are
   not, the fix is usually text, not aria.

4. THE PAYLOAD BLOCK.
   SchedulerRunDetailView.vue:121-125 is an unlabelled `<pre>` that scrolls horizontally. A scrollable
   region must be keyboard-reachable (tabindex="0") and needs an accessible name — its heading is
   right above it at :111-113, so associate them rather than inventing new copy. The `<VIcon
   icon="circle-info" :title="…">` at :114-119 is a tooltip that exists only on hover: a keyboard or
   screen-reader user never gets that explanation. Make the hint reachable.
   If S6 has run, the payload block now has an expand/collapse control — make sure it announces its
   state (aria-expanded) and that collapsing does not strand focus inside a hidden region.

5. THE FIXED PIXEL WIDTHS ON THE DASHBOARD.
   SchedulerNeedsAttentionView.vue:52, :66, :80 set `style="min-width: 180px; flex-basis: 180px"` on
   the three count cards, and AttentionJobList.vue:5 sets `style="min-width: 320px; flex-basis: 31%"`
   on each attention card. Below roughly 1000px the three attention lists cannot fit and the 320px
   floor forces horizontal scrolling of the whole page — the one thing that should never happen.
   Rework to Vuetify's grid or breakpoint-aware flex so the cards stack cleanly instead. CLAUDE.md's
   styling priority applies: component props first, then utility classes, and inline style only for
   one or two properties with no alternative — five inline layout styles is exactly the case it is
   warning about.
   Check the two info grids on the detail pages too: `repeat(auto-fit, minmax(220px, 1fr))` is
   already responsive and is probably fine — verify at 360px rather than changing it reflexively. If
   S4 has run, this CSS lives in one shared place now; fix it there.
   Also check the grids themselves at narrow widths. Both use BasicTable with `errorSummary` capped
   at `max-width: 320px` inline (JobRunHistory.vue:99) — see whether the table scrolls its own
   container or the page.

6. LIVE REGIONS FOR THINGS THAT CHANGE WITHOUT A CLICK.
   If S5 has run, the needs-attention dashboard now refreshes on a timer and shows an "updated X ago"
   line. Content changing under a screen-reader user with no announcement is disorienting; content
   announcing itself every minute is worse. Choose deliberately: an aria-live="polite" region for
   meaningful changes (a new failure appearing) and NOT for the ticking timestamp. If S5 has not run,
   skip this item and say so.
   The snackbars used throughout for action feedback are a framework component — check once whether
   Snackbar.vue announces, and if it does not, note it in your report rather than fixing it here. It
   is used app-wide and is outside this module's blast radius.

7. THE FILTER PANELS AND DIALOGS.
   Tab through FilterPanel on both grids and through ReplayConfirmDialog: focus must move into the
   opened panel/dialog, must not escape behind it, and must return to the trigger on close. These are
   framework components (FilterPanel.vue, MyDialog.vue) so most of this is not yours to fix — VERIFY,
   and report anything broken rather than patching a shared component from inside a module prompt.
   What IS yours: ReplayConfirmDialog's acknowledge checkbox is the safety gate on a destructive
   action. Confirm it is reachable and toggleable by keyboard alone, and that the disabled confirm
   button explains WHY it is disabled to a screen reader, not just visually.

DO NOT, in this prompt:
  - restructure any component or move code between files (that is S3/S4),
  - change copy, colours or icons beyond what an accessibility fix requires,
  - add aria attributes to things Vuetify already handles — an incorrect aria-label overrides a
    correct computed name and makes the page worse than leaving it alone,
  - modify shared framework components outside modules/scheduler/ (BasicTable, FilterPanel, MyDialog,
    Snackbar, ChipWithIcon). Report, do not patch. EXCEPTION: if S4 has run and moved a shell
    component into _common/component/, that file is yours.
```
